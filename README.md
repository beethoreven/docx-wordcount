# docx-wordcount

算 `.docx` 的字數／字元數／段落數，數字跟 Word「校閱 → 字數統計」對話框**完全一樣**，但不需要開 Word。有命令列版跟 Windows GUI 版（單一 `.exe`，不需安裝、不需網路）。

這個工具存在的理由：劇本殺文本常按文本量報價，需要一次查好幾個檔案；從 Word UI 一個一個開太慢，而把 `.docx` 丟給 LLM 直接問字數則永遠是估的、不會對。

## 命令列版

```bash
# 單檔／多檔／整個資料夾
python docx_wordcount.py "劇本.docx"
python docx_wordcount.py -r "D:\劇本"

# 貼進試算表（--tsv 印完整路徑，不會因同名檔案分不出來）
python docx_wordcount.py --tsv -r "D:\劇本"

# 注意：PowerShell 與 cmd 不會替外部程式展開通配字元，`*.docx` 會原樣傳進來。
# 要指定一批檔案就給資料夾，或自己展開：
python docx_wordcount.py (Get-ChildItem *.docx).FullName

# 對齊 Word 對話框「包含文字方塊、註腳及章節附註」那個勾選項
python docx_wordcount.py --include-notes --include-boxes a.docx
```

零依賴（只用 `zipfile` + `xml.etree`），一份檔案約 0.02 秒。

## GUI 版

`gui/wordcount_gui.py`，單一視窗，不需 Word、不需網路：

- 「選擇資料夾…」算資料夾第一層的所有 `.docx`（不進子資料夾）；「選擇檔案…」只算一個。
- 上半部是表格（字數／字元不計空白／字元含空白／中文字元／段落），可直接選取範圍 Ctrl+C。
- 下半部計算完成後自動產生一段可直接複製貼上的報價文字，格式固定為：

  ```
  【字數：
  健身教練：8250
  女大學生：8101

  總字數： 8250+8101=16351

  總報價：16351*16/1000=262】
  ```

  每個檔案後面的數字是**字元（含空白）**，不是字數。「單價（每千字）」是「複製整份表格」旁邊的欄位，預設 16，可調整（不能留空或輸入非數字，離開欄位時若無效會自動還原成 16）；改動單價會即時重算下方的報價文字。總報價採四捨五入。

打包成單一 exe：

```bash
cd gui
python -m PyInstaller --onefile --windowed --clean --name ScriptWordCount --paths .. wordcount_gui.py
```

輸出在 `gui/dist/ScriptWordCount.exe`（build 產物不進版控，見 `.gitignore`）。

## 交叉驗證

```bash
powershell -ExecutionPolicy Bypass -File verify_against_word.ps1 -Path "D:\劇本"
```

透過 COM 靜默開啟每個檔案、讀 Word 自己的 `ComputeStatistics()`，再跟 Python 的結果逐項比對。需要裝 Word，慢得多（每檔數秒）——這正是 Python 版存在的理由。**改動計數邏輯後一定要跑這個**，不要只靠讀程式碼判斷對不對。

## Word 的計數規則（實測反推，不要憑印象改）

以下每一條都是拿 Word 14.0 的 `ComputeStatistics()` 對受控測試檔量出來的，不是照文件或直覺推的。要動 `docx_wordcount.py` 之前先讀完這節。

### 字數

Word 逐字元分類，然後掃過整個段落：

1. **每個東亞寬字元自己算一個字。** CJK 表意文字、假名、諺文音節、注音、CJK 標點（`，。、「」〈〉《》`）、全形字元（`ＡＢＣ／～＆－`）、片假名中點（U+30FB、U+FF65）。所以「你好，世界。」是 **6 字**——全形標點也算。
2. **其餘字元連成一串算一個字。** 字母、數字、ASCII 標點、`…‥‒―‑─·`、`●○▪‣⁃§¶†‰°±×÷`、圈碼數字 `①②③`、羅馬數字 `ⅠⅡ`、emoji。`ABC-DEF` 是 1 字，`①②③` 也是 1 字。
3. **只有三個字元「算字元卻不算字」，而且會斷開連續串**：`–` U+2013、`—` U+2014、`•` U+2022。就這三個。這是逐一實測 50 個候選符號比對出來的，**不要用 Unicode 類別去推**——長得幾乎一樣的 U+2012、U+2015、U+2500、U+00B7、U+25CF 全都是普通的連續串成員。單獨一行的 `——` 是 2 字元、0 字。
4. **空白斷開連續串、不算字**：半角空格、定位字元、NBSP、全形空格 U+3000。
5. **手動換行 `<w:br/>` 斷開連續串，但完全不算字元**（連「含空白字元數」都不算）。
6. **四個零寬字元 Word 完全看不見**：`U+200B` 零寬空格、`U+200C` ZWNJ、`U+200D` ZWJ、`U+FEFF`。不算字元、不算字，**而且不會斷開連續串**（`A`+ZWSP+`B` 是 1 個字，不是 2 個）。這條要抓得很窄：軟連字號 `U+00AD`、`U+200E`/`U+200F` LRM/RLM、`U+2060` WORD JOINER、以及組合附加符號雖然同屬 Cf/Mn，Word **全部照算成一般字元**，不能一起處理掉。零寬空格在網頁複製貼上的文字裡很常見，劇本文本尤其容易帶進來。

段落之間不會連起來算，所以整份文件的數字就是各段相加——實測逐段相加等於文件總計，可以拿來當回歸測試。

### 三個真實檔案才會踩到的例外

這三條是「規則寫對了但真實檔案還是系統性少算」的原因：

1. **歧義寬度字元會隨 run 換邊。** Unicode 標為 ambiguous width 的字元（`·` `“”` `①` `Ⅰ`）沒有固定歸屬：所在 `<w:r>` 帶 `w:rFonts w:hint="eastAsia"` 時算東亞字元（1 字 + 1 中文字元），否則算連續串成員。**只看該 run 自己的屬性**——段落標記的 `rPr` 和 `docDefaults` 的 hint 都**不會**繼承下來（實測：某樂譜檔 60 個 `·`，Word 只算自己 run 帶 hint 的那 20 個）。例外中的例外：`–` `—` `•` 也是 ambiguous width，但永遠是分隔符，不受 hint 影響。
2. **自動編號的標號要算進去。** 清單前的 `1、`、`a)`、項目符號不在 `document.xml` 裡，要從 `numbering.xml` 重建（解析 `numPr` → `num` → `abstractNum` → `lvl` 的 `numFmt`/`lvlText`/`suff`/`start`，追蹤各層計數器），還要加上後面那個 `suff` 定位字元。清單密集的檔案漏掉這條會少算 5% 以上。編號也可能來自段落樣式而非直接格式，兩者都要查。
3. **統計範圍只有主要內容——本文 + 表格。** 頁首、頁尾、註解、隱藏文字（`<w:vanish/>`）**永不計入**；註腳、章節附註、文字方塊只有勾選才算（就是 `--include-notes` / `--include-boxes`）。實測：本文 3 + 表格 4 = 預設 7 字，勾選後 13 字。

### 字元數與段落數

- **字元數（不計空白）**＝所有字元減空白（含 U+3000）。
- **字元數（含空白）**＝所有字元；**段落標記不算**。
- **表格不產生額外字元**——2×2／3×2／1×4／4×1／3×3 都實測過，儲存格與列的結束標記一律算 0。
- **註腳／附註／欄位的參照標記算 1 個字元、0 個字。**
- **段落數的判定是「不計空白的字元數 > 0」**，不是「含空白字元數 > 0」。只含空白的段落（例如整段只有兩個全形空格 `　　`）Word 不算一段。實測依據：某劇本檔 Word 逐段資料裡 `chars>0` 的段數 = 196 = Word 報的段落數，而 `charsWS>0` 是 197。所以段落數會小於 `<w:p>` 元素的個數。

## 解析 XML 時的兩個坑

這兩個不是計數規則，是 OOXML 結構的坑，都實際踩過：

1. **文字方塊在 `document.xml` 裡存兩份。** `<mc:AlternateContent>` 底下 `<mc:Choice>`（DrawingML）與 `<mc:Fallback>`（舊版 VML）各一份相同文字。用 `element.iter()` 天真地掃會重複計算，而且把兩段文字黏在一起還會讓 token 數看起來「剛好」對不出來。只能走其中一支。
2. **`<w:pPr>` 裡的 `<w:tab>` 是定位點定義，不是定位字元。** 抽文字時整個跳過 `<w:pPr>` 和 `<w:rPr>`，否則會依定位點數量虛增「含空白字元數」（實測五個檔案各虛增 35）。

## 已知限制（哪些是實測、哪些是外推）

**分清楚這兩者很重要**——下面「外推」的部分是從少數幾個字元的實測結果推及整個 Unicode 區段，沒有逐一驗證過。要改動或依賴它們之前，先對相關字元跑一次 `verify_against_word.ps1`，不要因為它寫在表裡就當成已證實。

- **東亞字元區段大多是外推的。** `_EA_RANGES` 裡實際實測過的只有：CJK 統一表意（U+4E00–U+9FFF）、CJK 標點（U+3001–U+303F 的常見幾個）、平假名、片假名（含 U+30FC、U+30FB）、諺文音節（U+AC00–U+D7AF）、全形區的 U+FF01–U+FF60 幾個代表字元、半寬區的 U+FF65。其餘區段——U+2E80–U+2EFF、U+2F00–U+2FDF、U+2FF0–U+2FFF、U+3190–U+319F、U+31C0–U+31FF、U+3200–U+32FF、U+3300–U+33FF、U+A000–U+A4CF、U+A960–U+A97F、U+F900–U+FAFF、U+FE10–U+FE6F、U+FF61–U+FF9F 其餘部分、U+1F200–U+1F2FF、U+20000 以上——**一個字元都沒實測過**，純粹是「同區段應該同類」的推論。
- **編號格式只有兩種實測過。** `_format_number` 支援 `decimal`／`bullet`／羅馬數字／英文字母／中文數字／圈碼數字等，但真實檔案裡只出現過 `decimal` 與 `bullet`，其他分支從未跟 Word 對照過。遇到用中文數字或羅馬數字編號的檔案，先交叉驗證。
- **`--include-deleted` 完全沒有測試覆蓋。** 追蹤修訂的行為預設對應 Word 的「簡易標記」檢視（不算已刪除文字）；`--include-deleted` 是為「所有標記」檢視寫的，但從未跟 Word 實際比對過。另外注意：使用者的 Word 開在哪個檢視會影響 Word 自己報的數字，所以交叉驗證前要先確認檢視模式一致。
- **`--include-notes` / `--include-boxes` 只驗證過一份合成測試檔**，沒有真實檔案覆蓋。
- 編號的 `lvlRestart` 沒有實作，多層清單的重新編號時機可能與 Word 不同。
- 隱藏文字只認直接格式的 `<w:vanish/>`，不解析樣式繼承來的隱藏。
- 表格模式的檔名欄只印檔名（好讀），`--tsv` 印完整路徑（不會因為兩個資料夾有同名檔案而分不出來）。要程式化處理請用 `--tsv`。
- 只支援 `.docx`／`.dotx` 這類 OOXML；舊的 `.doc` 二進位格式不支援。

## 兩個環境層面的坑（已修，別改回去）

- **不要把輸出編碼交給環境決定。** 這支工具會印 CJK 檔名，而 Windows 的主控台預設碼頁是 cp950（Big5）。實測：清掉 `PYTHONIOENCODING` 之後，處理檔名含简体字「众」（U+4F17，Big5 沒有）的檔案會直接 `UnicodeEncodeError` 整個中止。開發機碰巧有機器層級的 `PYTHONIOENCODING=utf-8`，所以測不出來——但這是簡→繁專案的配套工具，简体檔名是常態。腳本開頭因此明確 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`，不繼承環境設定。
- **COM 物件要在 per-file 的 `finally` 裡關。** `ComputeStatistics` 若在 `Documents.Open` 成功之後拋出，沒有 per-file `finally` 的話那份 document 會留在共用的 Word 實例裡不關，多失敗幾次就累積一堆。

## 驗證狀態

計數引擎（`docx_wordcount.py`）目前的實測結果：130 個受控段落（每個隔離單一變數）全數吻合、25 份真實檔案的五項統計（字數／字元不計空白／字元含空白／中文字元／段落）**全部完全吻合**，其中 15 份是真正的劇本文本。GUI（`gui/wordcount_gui.py`）呼叫的是同一份未經修改的計數邏輯；GUI 自己新增的報價文字產生邏輯（`build_quote_text`）已用純函式單元測試驗證，逐字元跟一組真實報價範例核對過。

改動 `docx_wordcount.py` 後請用 `verify_against_word.ps1` 重跑，**而且要拿真正的劇本檔跑，不要只跑受控案例、也不要只拿手邊隨便找得到的 docx**。第一版就是這樣出錯的：當時的 10 份「真實檔案」是履歷、樂譜、報價單，全部通過，一拿真正的劇本文本就露出兩個 bug（零寬空格、段落數判定欄位用錯）——那些字元只在實際的工作語料裡才出現。
